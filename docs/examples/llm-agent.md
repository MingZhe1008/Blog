# 从 LLM 到 Agent：让模型从回答问题走向执行任务

第一次使用大语言模型时，我们通常把它当成一个问答工具：输入问题，等待答案。

但在实际工作中，我们需要的往往不只是一段回答。例如，整理项目中的待办事项、查询某条记录、分析错误日志，或者修改代码并验证结果。这些任务涉及外部数据、操作步骤和执行反馈。

Agent 的价值，就在于把模型的判断能力与外部工具连接起来，形成一个能够持续推进任务的执行过程。

## 1. LLM 与 Agent 有什么区别？

LLM 是 Agent 的核心组成部分，但二者并不等同。

| 维度 | LLM | Agent 系统 |
| --- | --- | --- |
| 主要职责 | 理解输入并生成输出 | 围绕目标选择操作、执行并检查结果 |
| 外部能力 | 取决于传入的上下文 | 通过工具访问文件、接口或其他系统 |
| 状态保存 | 单次调用本身不持久保存业务状态 | 由应用维护任务状态和执行记录 |
| 执行方式 | 一次或多次模型调用 | 根据反馈继续行动，直到完成或停止 |

可以用一个简化的关系理解：

> Agent 系统 = 模型判断 + 工具执行 + 状态管理 + 控制流程。

这不是严格的技术定义，但有助于拆解实现。

## 2. 从一个具体任务开始

假设我们要实现一个“项目待办整理助手”。

用户提出：

> 帮我检查这个项目里尚未完成的事项，并整理成一份清单。

这个任务可以拆成三个阶段：

1. 收集信息
    1. 查看项目说明和当前进度文档。
    2. 搜索源码中的 TODO 与 FIXME。
    3. 读取相关上下文，判断注释是否仍然有效。
2. 整理结果
    1. 合并重复事项。
    2. 区分缺陷、功能需求和维护任务。
    3. 为每项结果保留文件位置与判断依据。
3. 检查输出
    1. 确认清单与实际源码一致。
    2. 标出无法确认的事项。
    3. 明确本轮只做整理，没有修改项目。

这时，模型负责判断“下一步做什么”，工具负责真正读取文件和搜索内容，应用负责控制访问范围并保存执行记录。

## 3. 工具调用不是模型直接执行代码

工具调用可以理解为一种结构化请求。

例如，模型需要搜索项目里的待办标记时，可以生成：

```json
{
  "tool": "search_project",
  "arguments": {
    "pattern": "TODO|FIXME",
    "directory": "src"
  }
}
```

接下来由应用完成以下步骤：

1. 校验工具名称和参数。
2. 确认目标目录在允许访问的范围内。
3. 执行搜索。
4. 将搜索结果作为工具反馈交给模型。

工具反馈可能是：

```json
{
  "matches": [
    {
      "file": "src/services/task-service.ts",
      "line": 42,
      "text": "// TODO: 添加分页查询"
    }
  ]
}
```

模型拿到结果后，还需要继续读取相关实现。仅凭一条 TODO 注释，不能断言分页功能一定尚未完成。

## 4. 一个最小 Agent 执行循环

下面的伪代码展示了基本流程：

```python
MAX_STEPS = 8
state = create_task_state(user_request)

for step in range(MAX_STEPS):
    decision = model.decide(state)

    if decision.type == "finish":
        return decision.answer

    if decision.type == "ask_user":
        return request_user_input(decision.question)

    call = validate_tool_call(decision.tool_call)
    result = execute_tool(call)

    state.record(call, result)

return summarize_partial_result(state)
```

这个循环有几个需要注意的地方：

- 模型输出必须经过校验，再交给工具执行。
- 工具结果应包含成功、失败和必要的错误信息。
- 每次调用都需要记录，便于定位问题。
- 达到步数上限后，应说明进度和未完成事项。

步数限制只是最基本的边界。实际系统通常还需要设置总耗时、调用费用和重复失败次数限制。

## 5. 状态应该放在哪里？

不要把所有状态都交给聊天记录承担。

可以把状态分成三个层次：

1. 当前任务状态
    - 用户目标。
    - 已完成的步骤。
    - 尚未解决的问题。
2. 工具执行记录
    - 调用了什么工具。
    - 输入了什么参数。
    - 返回了什么结果。
3. 持久业务数据
    - 项目配置。
    - 用户明确保存的偏好。
    - 已确认的任务清单。

聊天上下文适合帮助模型理解当前任务，数据库和文件则负责保存需要长期保留的数据。

两者分工清楚后，即使模型调用失败，应用也能知道任务执行到了哪一步。

## 6. 固定流程，还是让模型自主选择？

并不是所有任务都需要开放式 Agent。

如果步骤已经明确，例如“读取表格 → 校验字段 → 生成报告”，可以由程序固定流程，只在提取、分类或总结环节调用模型。

如果下一步取决于执行反馈，例如排查一个未知错误，则可以允许模型在限定的工具集合中选择操作。

我的实现顺序会是：

1. 先用固定流程跑通任务。
2. 观察哪些分支无法提前写清楚。
3. 只把这些分支交给模型判断。
4. 根据实际失败案例逐步调整控制逻辑。

这样更容易知道，系统的复杂度究竟来自业务本身，还是来自过度设计。

## 7. 如何判断 Agent 做得好不好？

能返回一段流畅的文字，不代表任务已经完成。

对于待办整理助手，我会检查：

- [ ] 是否找到预先设置的关键待办？
- [ ] 是否把已经完成的事项误判为未完成？
- [ ] 是否为每个判断提供文件位置？
- [ ] 工具失败后，是否如实说明？
- [ ] 是否遵守只读范围？
- [ ] 是否在限制内结束任务？

评估时可以准备一组小型项目样例，分别包含正常情况、过时注释、重复待办和工具失败等场景。

每次修改提示词或控制流程后，使用相同样例重新检查，才能知道变化是否带来了改善。

## 8. 我会先做出的最小版本

第一版不必同时加入长期记忆、多 Agent 协作和复杂规划。

我会先完成：

1. 一个明确的目标：生成有依据的待办清单。
2. 三个只读工具：列出文件、搜索文本、读取文件。
3. 一个有步数与耗时限制的执行循环。
4. 一份可查看的工具调用记录。
5. 一组能够重复运行的评估样例。

当这个版本可以稳定处理真实任务后，再考虑增加写入、审批或其他能力。

## 结语

构建 Agent 时，最值得花时间的部分，往往是工具的边界、状态的保存方式，以及完成条件的定义。

模型提供判断，工具提供行动能力，应用负责把执行过程组织起来。只有这几部分共同工作，系统才能从“给出一个看起来合理的答案”，走向“完成一项可以检查结果的任务”。
